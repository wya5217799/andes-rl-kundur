statement: |
  R89-W1 (R09-副线 revival audit, zero ANDES TDS, pure file inspection):
  ANDES default `andes/cases/kundur/kundur_full.xlsx` (loaded by
  `V4 env._build_system()` line 245) has **all 4 GENROU machines + 15
  Lines at fn=60.0 Hz** (US grid base), whereas project
  `scenarios.contract.KUNDUR.fn=50.0` (paper Sec.II-A European 50 Hz).
  `base_env.py:441` does `freq_hz = omega * self.FN` (FN=50.0) to convert
  ANDES omega_pu to Hz, but ANDES integrates the system at 60 Hz
  physically (omega_pu normalised to its fn). Net effect:
  **env-reported max_df underreports physical max_df by factor
  50/60 = 0.833** (17% underreporting). To convert env-reported `freq_hz`
  to true physical Hz, multiply by 60/50 = 1.2.

  This is a CALIBRATION bug, not a TRAINING bug. The env is internally
  self-consistent (reward + obs + action all in env's "50 Hz scaled"
  units), so R57+ ckpt training is fine. The bug manifests only when
  comparing max_df numbers to paper benchmarks.

  Practical impact on R08 Finding 2 2× max_df residual:
  - Env V4 no_ctrl LS1 max_df = 0.189 Hz (CLM-0051 zero_g4_inertia=True)
  - Physical at 60 Hz = 0.189 × 1.2 = 0.227 Hz
  - Paper Fig.6 LS1 max_df = 0.13 Hz at 50 Hz
  - Ratio physical/paper = 0.227 / 0.13 = 1.75× (vs env/paper = 1.45×)
  - F1 fix makes the discrepancy LARGER, not smaller — so F1 alone is not
    the source of the residual. Other findings (F2 load topology,
    F3 D=0, F4 TGOV1 active) likely dominate.

  Locked in by `tests/test_v4_fn_consistency.py::test_andes_fn_matches_env_fn`
  (deliberately xfail strict; flips to pass when F1 is fixed in R90+).
