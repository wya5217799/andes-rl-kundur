## Why it matters

The project has now separated several failures:

- R265 found small physical opportunity in a hand-designed selector but
  unacceptable action movement;
- R267's only permitted smoother failed to retain the physical/action
  contract;
- R268's corrected learned residual completed safely but did not improve
  either co-primary mean;
- R269 refuted the convenient explanation that R268 omitted absolute frequency
  error from its reward.

Before another policy, reward, or graph architecture, the project must
establish whether the current inertia/damping inputs can produce a meaningful
physical improvement over tuned droop at all.  A disturbance-informed,
controller-agnostic oracle is not deployable, but it can measure an attainable
upper margin.  Without that margin, learning has no credible target.

## Pre-commitment for the future round

1. Reuse the R268 reference-feasible disturbances, physical endpoint code,
   droop prior, action bounds, and real-ANDES runner.
2. Begin with an offline/local sensitivity and identifiability audit.  Launch
   new ANDES trajectories only after freezing a low-dimensional,
   physics-interpretable action schedule and a strict evaluation budget.
3. Give the oracle disturbance identity and future knowledge so its result is
   explicitly an upper bound, not a deployable controller comparison.
4. Compare against measured droop on identical scenarios and report common
   frequency restoration, differential synchronization, failure, settling,
   safety peaks, action effort, and action variation.
5. Do not train a neural network, sweep RL algorithms, reuse a result-selected
   scenario bank as confirmation, or make topology/stability/manuscript claims.

## Decision direction

- If a prospectively bounded oracle cannot produce a material paired
  improvement in both physical modes without safety/action regression, close
  learned inertia/damping control on the current modified Kundur environment
  and pivot to a benchmark/model-validity contribution or a different
  actuator.
- If the oracle margin is material and repeatable across the fixed feasible
  envelope, retain the control problem but route the next question to
  observability/credit assignment, not another blind architecture sweep.
- The oracle result is an attainability diagnosis, never a claimed deployable
  method.
