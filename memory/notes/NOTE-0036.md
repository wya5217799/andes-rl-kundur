## Summary
R483 killed by cleanup 2026-08-26; watchdog auto-recovery + do-not-kill contract

## Key facts (claim candidates)
- 2026-08-26 01:54 local, all 18 R483 processes (16 workers + driver +
  launcher) died simultaneously with no OS-level record (no OOM, no reboot,
  no WSL restart, no event-log entry); user confirmed an attempted
  memory-cleanup was the likely cause. Last write was an ANDES output file
  cut off mid-write at 01:54:46.
- Loss was bounded: 32 completed cells (waves 1-2) were hash-validated and
  reused on resume (verified: 32/32 manifests valid, no cell re-trained);
  16 in-flight cells (an_cn_r1 seeds 507-522) lost ~1.6 h each and re-ran
  from scratch per the sealed recovery policy
  (preserve_partial_new_attempt_reuse_completed); 160 cells were pending.
- Mid-training resume from half.pt is NOT implemented and must not be added
  to R483: half.pt contains only agent weights (no replay buffer), a resumed
  cell would be a different training object and would contaminate the
  pre-registered factorial identity; any post-seal source change aborts the
  round. Wall loss (one wave ~3 h) is the floor for a valid experiment.
- Protection now in place: `tmp/andes/r483_watchdog.py` (detached watchdog,
  every 120 s checks driver liveness; on death with incomplete queue it
  relaunches the frozen launch-train --resume; halts without relaunch on
  retained failures/admission_halted; max 3 relaunches/hour to avoid a
  kill-loop; writes `tmp/andes/r483_watchdog_events.log`) and
  `tmp/andes/r483_PROTECTED.md` (do-not-kill contract + safe memory
  checklist). No userspace protection can block root-level kill -9 or
  `wsl --shutdown`; the watchdog is the recovery layer, not a shield.
- Lesson for infra: if a second round needs the same protection, generalize
  the watchdog into `memory/tools/`; do not duplicate it per round.
